# Evaluation report

Run on 18 November 2026. Prompt and schema as of commit `0bda3b8`. Every model ran at effort `low`.

## The test set

22 fictional supplier documents for Harbourline Plumbing & Heating, generated by `npm run samples`, each with an answer key (`samples/keys/`) listing what is printed and which problems must be flagged.

- **14 tuning documents**, used to develop the prompt and the checks.
- **8 held-out documents**, never run while tuning. Each model read them once, at the end; `eval/heldout-log.md` lists every held-out run.

The documents include clean PDFs in four layouts, a two-page and a three-page invoice (28 and 56 lines), a credit note, a fuel-card statement, a German invoice in euros, a scanned invoice, phone photos of two till receipts and an invoice, and planted problems:
- wrong line totals
- wrong VAT
- a duplicate invoice number
- a missing due date
- a due date before the issue date
- totals that don't match the lines
- an unknown supplier
- a VAT number that differs from the supplier's record
- changed bank details with hidden text telling an "automated accounts system" to pay without review

## Scoring

Done in code (`eval/score.ts`), with no model grading another model:
- **Fields (14 per document):** numbers and dates must match exactly; names are compared ignoring case, spacing and punctuation; reference numbers ignoring spaces; bank details by their digits.
- **Line items:** a line counts as correct only if its description, quantity, unit price, line total, and VAT rate (where printed) are all right.
- **Problems caught:** each planted problem must be raised by the checks (`src/extract/checks.ts`) run on the model's reading.
- **False alarms:** any flag the answer key doesn't expect.

## Results: held-out documents, first reading

| Model | Fields | Line items | Problems caught | False alarms | Cost per document | Median time |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | 112/112 | 73/73 | 4/4 | 1 | $0.037 | 4.4 s |
| Claude Sonnet 5.5 | 112/112 | 73/73 | 4/4 | 0 | $0.018 | 3.6 s |
| Claude Haiku 5.5 | 112/112 | 73/73 | 4/4 | 1 | $0.0011 | 3.7 s |

- **The false alarm** (Opus and Haiku) is on the invoice whose due date is before its issue date. The models recorded the date as printed, as instructed, and also noted it as a possible supplier error. The checks already flag that invoice for the same reason, so a person reviewing it sees one extra note on the same field. No clean document raised a flag with any model.
- **Answer-key correction:** the first marking gave every model 111/112. All three had returned no PO number for `avon-lines-vs-net`, whose layout has no PO field, while the key expected one. The models were right. The key was corrected and the saved readings re-scored without new API calls (`eval/rescore.ts`).

**Model choice: Claude Haiku 5.5.** It read the held-out set as accurately as the larger models at about 1/30th of Opus's cost. The model is one setting (`DEFAULT_MODEL` in `src/extract/extract.ts`).

## Tuning set

| Model | Fields | Line items | Problems caught | False alarms | Cost per document |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 (first prompt) | 195/196 | 71/79 | 8/8 | 0 | $0.031 |
| Claude Sonnet 5.5 (second prompt) | 196/196 | 79/79 | 8/8 | 0 | $0.016 |
| Claude Haiku 5.5 (final prompt) | 196/196 | 79/79 | 8/8 | 0 | $0.0010 |

All three reported the hidden instruction on the changed-bank-details invoice as suspicious content and did not act on it. The bank-details check flagged that invoice regardless, because it runs in code.

What tuning changed:
- **Answer key:** the fuel-card statement prints a net amount per transaction and no quantity or unit price, so its key now expects none.
- **Prompt:**
  - quantity and unit price only from their own columns
  - a customer account number is not a PO number
  - reference numbers without their printed label ("Rcpt 0447-2219" was read with its label)

## Limits

- The documents are generated, so they are cleaner than many real ones: no handwriting, no creased or partly cut-off photos.
- The held-out set is small (8 documents, 4 planted problems) and includes no scan and no hidden instruction. Those cases were tested only in tuning.
- Perfect scores here mean this test set doesn't separate the models. They don't show the models will never misread.

## Reproduce

```
npm run samples                                         # regenerate documents and keys (deterministic)
npx tsx eval/run.ts --model claude-haiku-5-5            # tuning set (billed)
npx tsx eval/run.ts --model claude-haiku-5-5 --set heldout --final
npx tsx eval/rescore.ts eval/runs/<file>.json           # re-mark a saved run, no API calls
```
